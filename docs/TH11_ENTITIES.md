# TH11 1.00a 实机实体观测

2026-10-17 修复：原实机 `StateReader` 只读标量，没有填充 `bullets` /
`enemy_positions`。74 维输入的 64 个弹幕特征因此恒为零。另一个问题是自机
窗口坐标和弹幕世界坐标混用。现已接入版本化实体布局，统一到 384×448 场地坐标。

## 布局与依据

布局来自本地 TH11 1.00a 可执行文件反汇编和运行时只读内存验证。
JSON 中地址相对主模块；以下绝对地址以基址 `0x400000` 为例。

| 对象 | 布局 |
| --- | --- |
| 弹幕管理器 | `read_u32(base + 0xA8D68)` |
| 弹幕数组 | 管理器 `+0x64`，2000 个槽，步长 `0x910` |
| 弹幕位置 | 槽内 `+0x43C/+0x440`，f32 |
| 弹幕状态 | 槽内 `+0x4B2`，u16；保留 1/2，排除 0/3 |
| 敌人管理器 | `read_u32(base + 0xA8D7C)` |
| 敌人链表头 | 管理器 `+0x68`；节点 `[对象指针, 下一节点, 前一节点]` |
| 敌人位置 | 对象 `+0x1070/+0x1074`，f32 |
| 敌人标志 | 对象 `+0x25BC`；排除掩码 `0x200020`（脚本控制器/移除中） |
| 自机旧字段 | `read_u32(base+0xA8EB4) + 0x3FC/+0x400` |
| 擦弹 | `base+0xA5754`，i32 |
| Boss 指针 | 敌人管理器 `+0x1C`，u32；0 表示当前无 Boss |
| Boss 血量 | Boss 对象 `+0x252C` (hp) / `+0x2530` (max)，i32 |
| Boss 标志 | Boss 对象 `+0x25BC`，u32；`0x100000` = 超时 |
| Boss 位置 | Boss 对象 `+0x1070/+0x1074`，f32（与敌人同布局，加 `(192,0)`） |
| 符卡管理器 | `base+0xA8D6C`；`+0x8DC` 起 `spell_id/flags/bonus` |

`combat` 块在读指针前先校验两处代码签名 `0x1B872 = 8b882c250000` 与
`0xCDC2 = f686e008000002`，任一不匹配就把整块标成 `error` 而不是猜地址。

**2026-10-21 实机复核**：两处签名均匹配；第一面道中（frame 2111）读到
`hp=12600/12600`、`位置 (192, -32)`（Boss 从场地上方入场），确认 Boss 血量与坐标
在真机可用。因此 `use_boss=True` 的两维观测（血量比 + 相对坐标）与老师的"对准
Boss"在真机上是有效的，不再只有躲避。注意 Boss 未入场时 `boss_id=0`，此时
`raw.boss_position` 不存在，特征按"无目标"编码。

`0x40AF9A` 读取弹幕管理器并加 `0x64`；`0x40AFD4` 读取状态；
`0x40B0B1` 以 `0x910` 递增遍历。`0x410540` 返回敌人链表头。
读取前验证前三处相应代码签名；不匹配的版本返回 error，不猜测地址。

坐标转换：自机旧字段减 `(32,16)`；弹幕/敌人世界坐标加 `(192,0)`。
所以自机中央 `(224,416)` 对外变为 `(192,400)`。`raw` 保留原始自机读数。
旧脚本中按窗口坐标调用 `move_to` 的目标需相应调整。

## 行为与限制

- 数组扫描全部 2000 个槽，不能用活动数当作连续数组长度。每次批量读取约 4.64 MB。
- 链表有遍历上限、环检测、空指针检查；检查有限坐标及管理器是否在读取中替换。
- `raw.entities` 区分 `ok`（可以确实为零）、`inactive`、`unconfigured`、`error`。
  失败不返回上一帧缓存，也不再把未知弹幕数序列化成零。
- 实机特征训练/游玩和辅助躲避会拒绝不可用观测。训练器及游玩脚本退出时释放按键。
- 兼容现有 74 维网络：最近 16 颗弹幕的相对位置/距离/有效位已接通；
  敌人完整坐标可通过状态接口获取，现有网络仍只使用敌人数量，不编码敌人位置。
- 只支持已匹配布局的 **TH11 1.00a 普通弹幕、敌人与 Boss 血量/坐标**。激光、无敌帧尚未接入；
  其它作品不能直接复用此布局。不是通关策略，也不保证旧 mock 模型可迁移。
- 内存批量读取不是暂停游戏的原子快照；读取失败会停止训练，需检查状态再重启。
- 未启用帧计数同步；控制仍基于时间。标题 Demo 也有实体，不能仅靠实体非空判断可控。
  测试通过重启进程、菜单导航及左右移动验证排除 Demo。

## 验证与使用

只读检查（不会启动游戏或发送按键）：

```powershell
.\.venv\Scripts\python.exe tools\validate_real_observation.py
```

只读检查 Boss 结构（签名 / 指针 / 血量 / 坐标；`--launch` 会由工具启动游戏）：

```powershell
.\.venv\Scripts\python.exe tools\probe_boss.py --launch
.\.venv\Scripts\python.exe tools\probe_boss.py --seconds 120   # 连续采样, 变化才打印
```

短真机训练验证（会重启 TH11；输出到独立时间戳目录，不覆盖原策略）：

```powershell
.\.venv\Scripts\python.exe tools\validate_real_observation.py --train --steps 300
```

正常训练与游玩：

```powershell
.\.venv\Scripts\python.exe examples\train.py --backend memory --game th11 --restart-process --episodes 50 --out .runtime\th11_entities
.\.venv\Scripts\python.exe tools\play_real.py --policy .runtime\th11_entities\policy --episodes 1
```

`--restart-process` 每局重启游戏，勿在需要保留的游玩进程上运行。沙箱可能阻止 SendInput
并报错误 5，应在允许访问桌面的同权限环境中运行，不需要修改 Windows 安全设置。

实测：300 步训练完成，无观测错误；最多 32 颗弹幕、18 个敌人，106 次非零弹幕输入，
完成一次有限值梯度更新。自机左右移动 x：192 → 300 → 201。另用保存模型运行
90 步真机游玩通过（例如 step 60：22 颗弹幕、13 个敌人）。
报告位于 `.runtime/entity_validation/20261017_221501_273903/report.json`。
这些是功能冒烟测试，不是学习效果或通关验证。

截图与内存读取非同步，PrintWindow/DPI 缩放也可能产生偏差；测试脚本的叠加图仅供
诊断，不作为像素级精度证据。使用 `raw.entities` 和数值验证判断读取是否成功。
